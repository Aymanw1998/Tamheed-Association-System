# Codex review: student to staff design (2026-11-19)

Actual run: `codex exec --sandbox read-only`, at the owner's request, against `1ff124e`. Spec: `docs/superpowers/specs/2026-11-19-student-to-staff-design.md`.

Reviewed against current HEAD `1ff124e`. The design needs changes before implementation.

1. **P1 — The audit ordering cannot provide “nothing changed.”** The [design:104](../../docs/superpowers/specs/2026-11-19-student-to-staff-design.md:104) creates the user, archives the student, changes programs, then writes the required audit row. An audit failure leaves those writes committed. `recordRequired` only returns a boolean; it provides no rollback and explicitly says to call it first ([audit.js:110](../../server/utils/audit.js:110)). Specify an atomic transaction or a durable operation journal with honest partial-completion responses. A final audit call alone cannot meet the promised failure contract.

2. **P1 — The proposed retry cannot recover all partial conversions.** The [design:106](../../docs/superpowers/specs/2026-11-19-student-to-staff-design.md:106) rejects linked/archived students, while retrying user creation encounters the existing-TZ rejection ([User.controller.js:664](../../server/Entities/User/User.controller.js:664)). A crash after user insertion but before linking leaves no durable conversion identity; a failure after moving some programs leaves a mixed roster. Persist the student-to-user association and conversion state, and define an idempotent resume operation that never creates another account. Protect the student and affected lessons against concurrent edits, deletion, and enrolment; existing lesson writes use version checks ([Lesson.controller.js:442](../../server/Entities/Lesson/Lesson.controller.js:442)). Test failures after each write, lost responses, and simultaneous submissions.

3. **P1 — Conversion and unarchive lack independently revocable permissions.** The [design:94](../../docs/superpowers/specs/2026-11-19-student-to-staff-design.md:94) authorizes conversion using `users.create` plus `students.viewAll`, and [design:152](../../docs/superpowers/specs/2026-11-19-student-to-staff-design.md:152) authorizes unarchive with a viewing capability. Neither operation exists in the [permission catalog:9](../../shared/permissions.json:9). Conversion also changes rosters whose existing routes separately require `lessons.roster` or `lessons.staffRoster` ([Lesson.route.js:50](../../server/Entities/Lesson/Lesson.route.js:50)). Define dedicated capabilities, server/button gates, and grant/revoke tests. Explicitly decide how the conversion capability authorizes its roster side effects.

4. **P2 — Replacing the roster corrupts the presentation of past attendance and creates extra historical marks.** “Past rows stay unchanged” is insufficient. `getSheet` builds every date from the **current** roster, then creates missing staff rows ([Attendance.controller.js:160](../../server/Entities/Attendance/Attendance.controller.js:160), [Attendance.controller.js:187](../../server/Entities/Attendance/Attendance.controller.js:187)). Those rows default to **present**. After conversion, reopening yesterday hides the old student row and inserts a staff-present row alongside it; exports can then count both. I reproduced this in memory. Define the effective attendance date, historical roster resolution, and conversion-day behavior before implementing [design:135](../../docs/superpowers/specs/2026-11-19-student-to-staff-design.md:135).

5. **P2 — An assistant in charge does not currently receive guide-equivalent attendance access.** Assistants lack `attendance.record` by default ([permissions.js:13](../../server/utils/permissions.js:13)); saving requires it ([Attendance.route.js:29](../../server/Entities/Attendance/Attendance.route.js:29)). `isOnLesson` being role-blind does not overcome that gate. Decide whether recording becomes an assistant default or a capability available specifically when responsible for a lesson, while preserving explicit revocation. Test the real route and UI, not just `isOnLesson`. Also, the attendance page excludes helpers from its lesson selector ([AttendancePage.jsx:142](../../apps/system/src/Components/Attendance/AttendancePage.jsx:142)); changing defaults broadly would not automatically give helpers a usable flow.

6. **P2 — Make-staff eligibility is specified mainly as UI behavior.** The server steps do not explicitly require normal student status, enforce the student’s TZ as the new account’s identity, restrict the conversion role to assistant/guide, or force an active account. Ordinary creation accepts a requested room ([User.controller.js:652](../../server/Entities/User/User.controller.js:652)), while staff attendance resolves only active users. The new-user TZ field is editable ([EditUser.jsx:456](../../apps/system/src/Components/User/EditUser.jsx:456)). A changed TZ could archive one person and create another; a non-active account would disappear from staff attendance. Enforce these invariants server-side and retain `canGiveFirstRole` hierarchy checks. Define the reverse user-to-student link too—the model section currently specifies only student-side fields.

7. **P2 — Archive enforcement needs an explicit read/write inventory, beyond hiding lists.** The following paths would otherwise keep finding or modifying an archived student:

   - Exact-TZ lookup and roster additions: [Student.controller.js:664](../../server/Entities/Student/Student.controller.js:664), [Lesson.controller.js:31](../../server/Entities/Lesson/Lesson.controller.js:31), including `list_tz` and unrestricted-ID additions.
   - Responsible-guide scope: [studentScope.js:18](../../server/utils/studentScope.js:18) and [lessonAccess.js:44](../../server/utils/lessonAccess.js:44). Keeping `main_teacher` preserves current access unless these paths change.
   - Direct edits, deletion, and photo changes: [Student.route.js:43](../../server/Entities/Student/Student.route.js:43). A read-only page does not protect these endpoints.
   - Automatic enrolment **and** student-movement enrolment: [educationalLesson.js:42](../../server/services/educationalLesson.js:42), [educationalLesson.js:50](../../server/services/educationalLesson.js:50).
   - Nightly absence creation and old absence-streak alerts: [Attendance.controller.js:428](../../server/Entities/Attendance/Attendance.controller.js:428), [alertJob.js:193](../../server/services/alertJob.js:193).
   - Annual grade promotion, which would keep changing the archived historical record: [gradePromotionJob.js:26](../../server/services/gradePromotionJob.js:26).
   - Already-issued parent-signature links, which still resolve and accept signatures: [InviteToken.controller.js:244](../../server/Entities/InviteToken/InviteToken.controller.js:244).

   Use explicit active/archive/history query modes. Globally hiding archived records in `StudentModelDef.get` would also break historical name resolution and duplicate-registration checks.

8. **P2 — Sport participation is a separate identity migration, not covered by moving `Lesson.list_students`.** Sport stores person IDs in player records, lesson rosters, attendance, login codes, and push subscriptions ([sportPeople.js:1](../../server/utils/sportPeople.js:1)). Its adapter currently returns both student and user records ([sportPeople.js:36](../../server/utils/sportPeople.js:36)). Merely hiding the student leaves existing Sport sessions valid unless authentication also changes ([SportPortal.auth.js:221](../../server/Entities/SportPortal/SportPortal.auth.js:221)); reminders use roster IDs directly ([sportPushJob.js:33](../../server/services/sportPushJob.js:33)). **Owner decision:** does “stays in every program as staff” include Sport? If yes, define continuity of membership, attendance, cards/passkeys, and historical statistics—staff players currently have no statistics.

9. **P2 — Active exclusion, historical reporting, and undo conflict.** The design excludes archived students from monthly counts but includes them in past-period reports. Monthly email already reports a past period and derives counts from attendance rows ([monthlySummaryJob.js:40](../../server/services/monthlySummaryJob.js:40)). Removing names alone leaves counts and unnamed absence entries. Removing archived IDs from current scope also removes their old marks from scoped exports ([Attendance.controller.js:514](../../server/Entities/Attendance/Attendance.controller.js:514)). Separately, undo preserves `main_teacher`, so the next save of an automatic educational lesson re-enrols the student ([Lesson.controller.js:453](../../server/Entities/Lesson/Lesson.controller.js:453)), contradicting “not added again automatically.” Decide historical visibility/counting and whether undo permits simultaneous student/staff participation.

10. **P2 — “A student’s responsible person is already guides/managers only” is false.** `isValidInstructor` accepts any active, non-hidden account ([Student.controller.js:31](../../server/Entities/Student/Student.controller.js:31)). The student form loads all users and its options filter by room, not role ([EditStudent.jsx:138](../../apps/system/src/Components/Student/EditStudent.jsx:138), [studentForm.js:18](../../apps/system/src/utils/studentForm.js:18)). Assistants can therefore already be `main_teacher`; their educational roster need not be empty. Enforce the owner’s rule in both places and decide how existing assistant assignments are handled. Also correct the blanket educational-roster description: `educationalRoster: "selected"` deliberately skips automatic enrolment ([educationalLesson.js:10](../../server/services/educationalLesson.js:10)).

11. **P2 — Educational-role validation must cover the resulting record and later role changes.** Validate merged `next.kind`/`next.teacher` before any write, so teacher-only updates and kind-only updates cannot bypass the rule ([Lesson.controller.js:379](../../server/Entities/Lesson/Lesson.controller.js:379)). Require an existing eligible active account, normalize `role`/`roles`, and fail closed on lookup failure. The current hidden-account check does not reject unknown or inactive ordinary IDs ([Lesson.controller.js:101](../../server/Entities/Lesson/Lesson.controller.js:101)). A later guide-to-assistant demotion also currently saves without examining educational lessons ([User.controller.js:1765](../../server/Entities/User/User.controller.js:1765)). **Owner decision:** block that demotion, require reassignment, or allow an explicitly invalid legacy state.

12. **P2 — `lessonParticipants` does not prevent the same teacher and helper.** It checks whether either responsible staff member also appears in `list_users`; it never compares teacher against helper ([lessonParticipants.js:18](../../server/utils/lessonParticipants.js:18)). An in-memory check with identical teacher/helper and an empty participant list returns no clash. Once assistants appear in both selectors, this becomes an ordinary selectable conflict. Add explicit create/update server validation; the assertion at [design:72](../../docs/superpowers/specs/2026-11-19-student-to-staff-design.md:72) is incorrect.

13. **P2 — AI attendance flows omit staff participants.** The regular sheet, save API, nightly job, and Excel attendance export already support `list_users`. However, `propose_attendance` requires `studentId` ([propose_attendance.js:23](../../server/services/assistant/tools/propose_attendance.js:23)); action preparation validates only `list_students` ([actionRunner.js:124](../../server/services/assistant/actionRunner.js:124)); summaries discard rows without a matching student ([attendance_summary.js:78](../../server/services/assistant/tools/attendance_summary.js:78)); and lesson listings expose only student counts ([list_lessons.js:63](../../server/services/assistant/tools/list_lessons.js:63)). Extend discovery, proposals, approval/revalidation, and summaries with distinct user IDs, or explicitly exclude staff attendance from the promised assistant-tool support.

14. **P2 — Prefilling the photo does not copy it safely.** `EditUser` removes `photo` from the creation payload ([EditUser.jsx:357](../../apps/system/src/Components/User/EditUser.jsx:357)); a URL is treated as “keep,” not an upload ([photoChange.js:5](../../apps/system/src/utils/photoChange.js:5)). Simply prefilling the form therefore loses the photo. Sharing the original URL instead creates a different problem: replacing the staff photo deletes the previous Drive file, breaking the archived student’s photo ([User.controller.js:2151](../../server/Entities/User/User.controller.js:2151)). Specify an independent copy or shared-file ownership and cleanup.

15. **P2 — The combobox accessibility contract is incomplete.** [Design:70](../../docs/superpowers/specs/2026-11-19-student-to-staff-design.md:70) lists some attributes and keys, but omits the input’s accessible name, `aria-controls`, autocomplete semantics, option IDs/selection, error association, and focus behavior after filtering or removing the assistant group. Preserve the current label association ([EditLesson.jsx:396](../../apps/system/src/Components/Lesson/EditLesson.jsx:396)). Specify DOM focus remaining on the input, valid active-descendant references, Tab/blur behavior, and Enter selecting without submitting the form. Distinguish typed text from the committed user ID. Add keyboard and screen-reader checks following the [W3C combobox pattern](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/).

16. **P3 — The wording inventory and public-registration assumption need correction.** Additional program wording remains in [LessonParticipants.jsx:15](../../apps/system/src/Components/Lesson/LessonParticipants.jsx:15), [excelExport.js:77](../../apps/system/src/utils/excelExport.js:77), and the teacher-required validation at [EditLesson.jsx:195](../../apps/system/src/Components/Lesson/EditLesson.jsx:195). Public registration does **not** return an “already registered” answer: an existing TZ receives the same generic success response as a new submission ([InviteToken.controller.js:414](../../server/Entities/InviteToken/InviteToken.controller.js:414)). Preserve that privacy behavior for archived students.

The named attendance/report reminder targeting, weekly-task ownership, wall-display name lookup, and lesson-access predicate are otherwise role-blind; the permission and participant-flow gaps above are the material exceptions.
