# IT Site Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** IT users, above everyone, do every sensitive action from a separate site at `it.tamheed-ramla.org`; 000000000 becomes the secret emergency account that also manages the IT users; administrators keep only everyday work, role changes and password resets below their rank; every student/user list shows a profile photo.

**Architecture:** One server, one database. The IT flag lives on the user record, apart from the everyday role. The server builds two kinds of actor: the everyday actor (today's `loadActor`, which never carries IT keys) and the IT actor (`requireIt`, from a separate cookie session signed with `IT_SESSION_SECRET`, accepted only for `IT_HOST`). The IT site (`apps/it`, React like `apps/sport`) talks only to `/api/it/*`, which reuses the existing user, audit, Drive, lock and push controllers with the IT actor.

**Tech Stack:** Node/Express, MongoDB through `server/Entities/api.js`, node:test; React 18 + react-scripts 5 (CRA) for `apps/system`, `apps/sport` and the new `apps/it`.

**Spec:** `docs/superpowers/specs/2026-11-03-it-site-design.md`

## Global Constraints

- One server (`server/`), one database. New env: `IT_HOST`, `IT_SESSION_SECRET`. Fail closed when `IT_SESSION_SECRET` is missing (like `SPORT_SESSION_SECRET` in `SportPortal.auth.js`).
- Every IT check is on the server: valid IT session + user is IT + not blocked + request host is `IT_HOST`.
- An IT user is never touched by another IT user or by an administrator (account level); only 000000000 does that.
- Administrators never change permissions; they change roles and reset passwords of lower rank only.
- 000000000 does everything IT does, plus managing IT users; its email code goes to `SYSTEM_ADMIN_EMAIL`; every sign-in of it alerts `SYSTEM_ADMIN_EMAIL` and is audited.
- No sign-up on the IT site. A user without a real email (empty or the model's `test@test.com` default) cannot be made IT.
- Public repository: no secrets, real ID numbers or passwords in code, tests, docs or the review log; tests use synthetic values.
- UI text Arabic. Follow the existing code style; CRLF files keep CRLF.
- Commits: one per task, message proposed in the task; no co-author trailer.
- Record each task in `docs/AI_REVIEW_LOG.md` (Codex review pending until it answers).
- Push only after Task 8: Tasks 3 and 6 move routes, so the steps in between are not meant to be deployed alone.

## Review Focus

1. An IT user reaches an everyday route (`/api/user/...`) with an everyday token and expects IT power there: must get only his everyday role's keys. → Task 2 test `everyday actor never carries IT keys, even for an IT user`.
2. An administrator edits the email or resets the password of an IT user who is also a guide (takeover of the IT sign-in): must be refused. → Task 3 test `an administrator cannot touch an IT user's account`.
3. A valid IT cookie sent to the IT API under another host (system or sport address): must be refused. → Task 5 test `IT routes refuse any host but IT_HOST`.
4. An IT user blocked or removed while signed in: the next IT request is refused at once (no waiting for the cookie to expire). → Task 5 test `a blocked or removed IT user is signed out on the next request`.
5. Old `permissionGrants` holding IT keys (granted by the system account before this change): they stop working in the everyday app and are listed by the migration. → Task 2 test `stored IT-key grants are ignored`, Task 9 test.

**Interfaces:**
- Produces (from `utils/permissions.js`):
  - `PERMISSION_TREE.users` gains `"resetPassword"`.
  - `IT_KEYS: Set<string>` = `permissions.manage`, `users.passwords` (now: *view* a password), `users.unlock`, `audit.view`, `storage.drive`, `systemRecovery.reset`. Replaces `DANGEROUS_KEYS` (keep `DANGEROUS_KEYS` as an alias export until Task 8 removes the last users).

  - `canAssignRole(actor, target, role)`: IT actor may also give **himself** an everyday role (the only self exception).
  - `validatePermissionChange(...)`: only an IT actor (`actor.it`); grantable = `ALL_KEYS` minus `IT_KEYS`.
  - `canResetPassword(actor, target): boolean` — IT actor: `canManageTarget`; everyday actor: holds `users.resetPassword`, target of lower rank, not IT, not self.

### Task 5: IT sign-in and the IT actor

**Files:**
- Create: `server/Entities/It/It.auth.js` (factory `createItAuth(deps)` like `SportPortal.auth.js`), `server/Entities/It/ItLoginCode.model.js` (unique `userTz`, TTL on `expiresAt`), `server/middleware/requireIt.js`
- Modify: `server/Entities/User/User.controller.js` (export `verifyPasswordAndMaybeUpgrade`), `server/utils/sendEmail.js` (`sendItLoginCodeEmail(to, code)`), `server/server.js` (indexes), `server/config/.env.example` (`IT_HOST`, `IT_SESSION_SECRET`)
- Test: `server/test/it-auth.test.js`

**Interfaces:**
- Produces:
  - `POST /api/it/login { tz, password }` → always `{ ok: true, message }` (generic, never says why); when the password is right, the user is active, IT, not blocked and has a real email: a 6-digit code (`generateOtp6`), stored hashed, 10 minutes, 5 tries, emailed to the user's email — to `SYSTEM_ADMIN_EMAIL` for the system account. Wrong passwords count in `utils/loginLockout` as on the everyday login.
  - `POST /api/it/verify { tz, code }` → sets cookie `it_session` (httpOnly, secure, sameSite strict, path `/api/it`, 12 h), JWT `{ sub: tz, typ: "it", iat }` signed with `IT_SESSION_SECRET`; code is single-use. System account: `sendSystemAdminEmail(SYSTEM_ADMIN_EMAIL, …)` alert and audit row `module: "it", action: "sign_in"`.
  - `POST /api/it/logout` clears the cookie. `GET /api/it/me` → `{ tz, name, isSystem, photo }`.
  - `requireIt` (middleware): host is `IT_HOST` (`req.hostname`, same comparison as `utils/sportHost.js` `isSportHost`), cookie valid, user active, `isIT`, not blocked, token not older than the last password change or IT removal (`tokenIsStale`-style on `itSince`/`itBlockedAt`) → `req.actor = { id, tz, name, isSystem, it: true, permissions: itPermissions(user, { isSystem }), user }`; else 401 `IT_SIGNED_OUT` (or 404 for another host).
