# الصلاحيات المختلطة، حساب النظام، حظر الدخول وسجل التغييرات: التصميم

- **التاريخ:** 2026-10-17
- **الحالة:** بانتظار مراجعة صاحب المشروع
- **المنفّذ:** Claude · **المراجع:** Codex (عند توفره)

## الهدف ولماذا

اليوم الدور يحدد كل شيء: كل من عنده دور `ادارة` يرى ويفعل كل ما تسمح به الإدارة. صاحب
المشروع يريد:

- ألا يرى كل مدير قسم المالية والتقارير المالية (قسم قادم).
- أن يكون إضافة ولد أو إرسال رسائل للأهل متاحًا لمديرين اثنين فقط مثلًا.
- عند إضافة قسم الرياضة (قريبًا): جزء من الإدارة وجزء من المرشدين فقط يدخلونه.
- أن يكون لكل حساب، فوق دوره، صلاحيات خاصة تُفتح وتُغلق بيد حساب النظام أو من يعيّنه.

الفكرة: **الدور يعطي نقطة بداية، والصلاحيات الخاصة لكل حساب تضيف أو تسحب.**

## ما هو موجود اليوم

- **الأدوار:** `ادارة`، `مرشد`، `مساعد` في `user.roles` (مصفوفة). الأدوار موجودة داخل
  الـ access token (صالح يومًا كاملًا، `server/utils/jwt.js`)، و`requireRole` في
  `server/middleware/authMiddleware.js` يقرأها من الـ token وليس من قاعدة البيانات.
- **فحص "هل هو مدير" مكرر ثلاث مرات:** `server/utils/vehicleRules.js`،
  `Report.controller.js`، `Storage.controller.js`، وكذلك `ADMIN_ROLES` في الـ middleware.
- **صلاحيات لكل حساب موجودة في قسمين فقط:**
  - المركبات: `user.vehiclePermissions` (`view`, `edit`, `compliance`, `documents`,
    `archive`). المدير يملكها كلها تلقائيًا.
  - الملفات: `user.storagePermissions` حسب المسار (`view`/`create`/`update`/`delete`).
- **الحماية الحالية في المسارات:**

| القسم | العملية | من مسموح اليوم |
| --- | --- | --- |
| الطلاب | عرض | كل مسجّل دخول (كل الطلاب) |
| الطلاب | إضافة، حذف | `ادارة` |
| الطلاب | تعديل، صورة | `ادارة`، `مرشد` |
| رابط تسجيل الأهل | عرض/تجديد | `ادارة` |
| الدروس | عرض | كل مسجّل دخول |
| الدروس | إضافة، تعديل، قائمة الطلاب | `ادارة`، `مرشد` |
| الدروس | حذف، نسخ شهر، حذف شهر | `ادارة` |
| الحضور | عرض | كل مسجّل دخول |
| الحضور | حفظ | `ادارة`، `مرشد` |
| التقارير | إنشاء، تعديل (تقاريره فقط لغير المدير) | الأدوار الثلاثة |
| التقارير | حذف، رؤية تقارير الآخرين | `ادارة` |
| المستخدمون | قائمة، إضافة، حالة، حذف، صلاحيات الملفات | `ادارة` |
| لوحة الإعلانات | كل شيء | `ادارة` |
| المركبات | حسب `vehiclePermissions` | المدير تلقائيًا |
| ربط Google Drive | | حساب النظام فقط (`SYSTEM_ADMIN_TZ`) |

- **حساب النظام:** `SYSTEM_ADMIN_TZ` في البيئة. اليوم يُستعمل فقط لربط Google Drive.
- **الدروس:** كل درس هو حدث بتاريخ (`name`, `date`, `teacher`, `helper`, `room`,
  `list_students`). لا يوجد كيان "حوزة/نادٍ" منفصل.
- **الطالب:** لا يوجد حقل "المرشد المسؤول".
- **تسجيل الدخول:** حدّ معدل (`authRateLimit`) فقط. لا عدّاد محاولات فاشلة لكل حساب.
- **سجل تغييرات:** موجود للمركبات فقط (`GET /api/vehicle/:id/audit`).

## مشاكل أمنية يجب إصلاحها أولًا

هذه ليست طلبًا جديدًا، لكن بدونها لا معنى للصلاحيات ولا للحظر:

1. **كلمة مرور عامة:** في `login` (`User.controller.js`) يُقبل الدخول إذا كانت كلمة المرور
   تساوي `process.env.Tamheed_Pass`. هذا يفتح كل حساب، بما فيه حساب النظام.
2. **الدخول بالـ hash:** نفس السطر يقبل `user.password === password`، أي من يعرف الـ hash
   المخزَّن يدخل به. و`GET /api/user/viewPassword/:tz` يعرض للمدير الـ hash المشفّر
   (`canViewEncrypted`). معًا: كل مدير يستطيع الدخول لأي حساب.
3. **صور المستخدمين:** `POST /api/user/upload-photo/:tz` و`DELETE /api/user/photo/:tz` بلا
   فحص دور. على المنفّذ التأكد أن الـ controller يسمح فقط لصاحب الحساب أو لمن يملك
   `users.edit`.

**القرار:** إزالة البندين 1 و2 بالكامل، وإزالة `viewPassword` (أو جعله يعيد فقط إن كانت كلمة
مرور موجودة، بلا أي قيمة). يُصلَح البند 3 حسب ما يجده المنفّذ.

**تنبيه للنشر:** إزالة البند 1 تعني أن كلمة المرور العامة لن تعمل بعد الآن. قبل النشر يجب أن
يعرف صاحب المشروع كلمة مرور حساب النظام الحقيقية، أو أن يكون `SYSTEM_ADMIN_EMAIL` مضبوطًا
للاستعادة.

## القرارات (من صاحب المشروع)

| الموضوع | القرار |
| --- | --- |
| المبنى | قسم ← أقسام فرعية/عمليات. فتح قسم = فتح كل ما فيه. يمكن إغلاق عمليات بعينها. إغلاق القسم يغلق كل ما فيه |
| الدور | لكل حساب دور واحد. الدور يفتح أقسامًا عامة، ثم تُضاف أو تُسحب صلاحيات للحساب نفسه |
| أقسام لا تأتي من أي دور | الرياضة والمالية: تُمنح لأشخاص بعينهم فقط، لا "لكل المرشدين" ولا "لكل الإدارة" |
| ترقية أو دور مساوٍ | تبقى الصلاحيات الخاصة، وتُضاف صلاحيات الدور الجديد. ثم سؤال: "إضافة صلاحيات الآن أو لاحقًا؟" الآن ← شاشة الصلاحيات. لاحقًا ← الخروج من الشاشة بعد التأكيد |
| تنزيل الدور | تُغلق صلاحيات الدور القديم **والصلاحيات الخاصة كلها**. تبقى فقط صلاحيات الدور الجديد |
| من يغيّر الصلاحيات | حساب النظام، ومدير صلاحيات يعيّنه النظام |
| مدير الصلاحيات | يغيّر للآخرين فقط، لا لنفسه. لا يستطيع إعطاء ما ليس عنده، ولا إعطاء "إدارة الصلاحيات" لأحد |
| تعديل المستخدمين | المدير يعدّل تفاصيل المرشدين فقط (ومن تحتهم)، لا مديرًا آخر |
| الصلاحيات الخطرة | تغيير الدور، إدارة كلمات المرور، والصلاحيات: للنظام فقط، أو لمدير موثوق أعطاه النظام هذه الصلاحيات. لا أحد يغيّر دوره هو |
| ما يراه المرشد | الطلاب الذين هو مسؤول عنهم (يُختار "مرشد مسؤول" عند إضافة الطالب) + طلاب الحوزات/الدروس التي هو فيها. المرشد قد يكون في عدة حوزات |
| قسم الرياضة | كحوزة كبيرة: كل من فُتح له القسم يرى كل ما فيه |
| سجل التغييرات | كل إضافة/تعديل/حذف في كل الأقسام (طلاب، مستخدمون، تقارير، ملفات ومجلدات بما فيها تغيير الاسم...). يراه النظام والمدراء المخوّلون فقط |
| حساب النظام | لا تتغير صلاحياته، لا يظهر لأي مستخدم ولا في أي قسم أو قائمة. أفعاله تُسجَّل باسم "النظام" |
| كلمة مرور النظام | تغيير إلزامي كل شهر |
| استعادة حساب النظام | عبر بريد النظام الحقيقي (يُضبط في `SYSTEM_ADMIN_EMAIL`). مدير مُنح صلاحية الاستعادة يستطيع تشغيلها بعد 3 محاولات فاشلة أو أكثر، والكلمة المؤقتة تذهب للبريد فقط. ولشخص IT طريق وصول في الحالات الحرجة |
| حساب النظام والحظر | **لا يُحظر أبدًا** |
| حظر الدخول | بعد 5 محاولات فاشلة يُحظر الحساب (كل الحسابات ما عدا النظام). لا استعادة عبر البريد. رسالة بالعربية: راجع قسم تكنولوجيا المعلومات في الجمعية |
| صلاحيات مؤقتة | ليست الآن |
| الأقسام الحساسة غير المالية | لم تُحدَّد بعد |

## ليس ضمن هذا العمل

- الدردشة الداخلية، المجموعات (مثل مجموعات البريد)، وإرسال تقرير لأشخاص أو مجموعات. هذا
  مشروع منفصل بعد هذا.
- بناء قسم المالية وقسم الرياضة نفسيهما. هنا فقط نحجز لهما مكانًا في شجرة الصلاحيات.
- صلاحيات مؤقتة بتاريخ انتهاء.
- تغيير نموذج صلاحيات الملفات حسب المسار (`storagePermissions`). يبقى كما هو.

## ما يجب ألا يحدث (فشل حتى لو "يعمل")

- مستخدم يفقد وصولًا كان عنده يوم النشر بلا قرار من أحد.
- مدير صلاحيات يرفع صلاحياته بنفسه، مباشرة أو عبر شخص آخر.
- حساب النظام يظهر في قائمة مستخدمين، أو كمرشد في درس، أو كاسم في سجل.
- صلاحية سُحبت وما زالت تعمل يومًا كاملًا حتى ينتهي الـ token.
- الواجهة تخفي زرًا والخادم يسمح بالعملية. **الخادم هو الحَكَم دائمًا.**

## الجزء 1: شجرة الصلاحيات

مفتاح كل صلاحية نص بنقاط: `قسم` أو `قسم.عملية`. امتلاك القسم يعني امتلاك كل عملياته.

| القسم | المفتاح | العمليات |
| --- | --- | --- |
| لوحة التحكم | `dashboard` | `view` |
| التقويم | `calendar` | `view` |
| الطلاب | `students` | `view`, `viewAll`, `create`, `edit`, `delete`, `photo`, `parentLink` |
| الدروس | `lessons` | `view`, `create`, `edit`, `roster`, `delete`, `copyMonth` |
| الحضور | `attendance` | `view`, `record` |
| التقارير | `reports` | `create`, `editOwn`, `viewAll`, `editAll`, `delete`, `exportPdf` |
| المركبات | `vehicles` | `view`, `edit`, `compliance`, `documents`, `archive` (نفس الموجود) |
| الملفات | `files` | `use`, `manageAll` (داخل الملفات تبقى صلاحيات المسار كما هي) |
| لوحة الإعلانات | `notices` | `view`, `post`, `runCheck` |
| المستخدمون | `users` | `view`, `create`, `edit`, `approve`, `delete`, `changeRole`, `passwords`, `unlock` |
| الذكاء الاصطناعي | `ai` | `use` |
| الصلاحيات | `permissions` | `manage` |
| سجل التغييرات | `audit` | `view` |
| استعادة النظام | `systemRecovery` | `reset` |
| الرياضة (محجوز) | `sports` | تُحدَّد عند بناء القسم |
| المالية (محجوز) | `finance` | تُحدَّد عند بناء القسم |

- `students.view` بلا `viewAll` = يرى فقط طلابه (الجزء 4). `viewAll` = كل الطلاب.
- `files.manageAll` = النطاق الشامل الذي يملكه المدير اليوم في `Storage.controller.js` (يرى مجلدات
  كل المستخدمين ويتجاوز صلاحيات المسار)، ويشمل تعديل `storagePermissions` لغيره
  (`PATCH /:tz/storage-permissions`). **قراري.**
- المركبات: نفس قاعدة اليوم، لا عملية بلا `vehicles.view`.
- الشجرة معرّفة في الكود في مكان واحد. قسم جديد = إضافة سطر، والشاشة تعرضه تلقائيًا.

## الجزء 2: صلاحيات كل دور (البداية)

**القاعدة:** صلاحيات الدور = ما يملكه الدور اليوم بالضبط، حتى لا يخسر أحد شيئًا يوم النشر.

| | `ادارة` | `مرشد` | `مساعد` |
| --- | --- | --- | --- |
| `dashboard`, `calendar` | ✓ | ✓ | ✓ |
| `students` | كل العمليات | `view`, `edit`, `photo` | `view` |
| `lessons` | كل العمليات | `view`, `create`, `edit`, `roster` | `view` |
| `attendance` | كل العمليات | `view`, `record` | `view` |
| `reports` | كل العمليات | `create`, `editOwn`, `exportPdf` | `create`, `editOwn`, `exportPdf` |
| `vehicles` | كل العمليات | - | - |
| `files.use` | ✓ | ✓ | ✓ |
| `files.manageAll` | ✓ | - | - |
| `notices` | كل العمليات | - | - |
| `users` | `view`, `create`, `edit`*, `approve`, `delete`* | - | - |
| `ai.use` | ✓ | ✓ | ✓ |

\* `users.edit` و`users.delete` (وكذلك تغيير الحالة) تعمل فقط على هدف **أقل رتبة** من المنفّذ:
المدير يعدّل ويحذف المرشدين والمساعدين، لا مديرًا آخر. وليس على من يملك صلاحية خطرة
(القائمة التالية) إلا للنظام.

**الصلاحيات الخطرة: لا تأتي من أي دور أبدًا، ويمنحها النظام فقط:**
- `users.changeRole`: تغيير دور حساب آخر.
- `users.passwords`: تعيين كلمة مرور جديدة لحساب آخر. (لا أحد "يرى" كلمة مرور: هي مخزّنة
  مشفّرة ولا يمكن قراءتها. "إدارة كلمات المرور" = إعادة تعيين فقط.)
- `users.unlock`: فك حظر.
- `permissions.manage`, `audit.view`, `systemRecovery.reset`.

**لا تأتي من أي دور، وتُمنح لشخص بعينه:** `sports`, `finance`.

**قراري (للمراجعة):** المرشد والمساعد اليوم يرون كل الطلاب. بعد الجزء 4 سيرون طلابهم فقط.
هذا تغيير مقصود بطلبك، وليس خسارة عرضية، لذلك لا يأخذون `viewAll`.

**قراري:** صلاحيات الأدوار تُحسب من الكود عند كل طلب ولا تُنسخ إلى الحساب. لذلك تعديل
صلاحيات دور في الكود يسري على كل أصحاب الدور. الأقسام الحساسة لا تدخل أي دور أصلًا.

## الجزء 3: الصلاحيات الخاصة لكل حساب

### التخزين

حقلان جديدان في المستخدم:

- `role`: نص واحد (`ادارة` | `مرشد` | `مساعد`).
- `permissionGrants`: مصفوفة مفاتيح ممنوحة فوق الدور.
- `permissionRevokes`: مصفوفة مفاتيح مسحوبة.

**قراري:** يبقى `roles` (المصفوفة) لفترة الانتقال ويُملأ بعنصر واحد = `role`، حتى لا ينكسر
كود قديم يقرأه. كل الفحوص الجديدة تقرأ `role`.

### الحساب

```
الفعّالة = (صلاحيات الدور ∪ الممنوحة) − المسحوبة
```

- منح قسم = منح كل عملياته.
- سحب قسم = سحب كل عملياته، حتى لو مُنحت عملية منه على حدة.
- يمكن منح قسم ثم سحب عملية واحدة منه.
- حساب النظام: كل الصلاحيات دائمًا، ولا تُقرأ حقوله.

### تغيير الدور

ترتيب الأدوار: `ادارة` (3) > `مرشد` (2) > `مساعد` (1).

- **ترقية أو نفس المستوى:** `permissionGrants` و`permissionRevokes` تبقى. الدور الجديد يضيف
  صلاحياته. بعد الحفظ نافذة: "هل تريد إضافة صلاحيات الآن أو لاحقًا؟"
- **تنزيل:** تُفرَّغ `permissionGrants` و`permissionRevokes`. يبقى فقط الدور الجديد. قبل
  الحفظ تحذير يوضح أن كل الصلاحيات الخاصة ستُحذف، ثم نفس النافذة.
- **من يغيّر الدور:** النظام، أو من يملك `users.changeRole`. لا أحد يغيّر دوره هو.
  **قراري:** صاحب `users.changeRole` يعيّن فقط دورًا يملك هو كل صلاحياته، ولا يغيّر دور من
  يملك صلاحية خطرة (هذا للنظام فقط).

### التسجيل الذاتي والموافقة (قراري)

اليوم من يسجّل نفسه (`POST /register`) يختار دوره، والموافقة (`changeRoom`) تفعّله بنفس الدور.
هذا يسمح بتجاوز قاعدة "لا ترفع أحدًا فوقك". لذلك:
- صفحة التسجيل لا ترسل دورًا، والخادم يتجاهله.
- عند الموافقة يختار من يوافق الدور، تحت نفس قاعدة تغيير الدور.
- `PUT /api/user/:tz` (`putU`) لا يقبل `roles` ولا `role` ولا حقول الصلاحيات. الدور فقط عبر
  `PUT /:tz/role`.

### مدير الصلاحيات

- هو من يملك `permissions.manage`. يمنحها فقط حساب النظام.
- لا يغيّر صلاحياته هو.
- **قراري:** لا يغيّر صلاحيات مدير صلاحيات آخر. هذا للنظام فقط.
- لا يمنح مفتاحًا ليس عنده (يُفحص على الصلاحيات الفعّالة له).
- لا يمنح أبدًا أي صلاحية خطرة (الجزء 2). هذه للنظام فقط.
- يستطيع السحب من الآخرين لكل ما يستطيع منحه.

### متى تسري

- **قراري:** الخادم يقرأ الدور والصلاحيات من قاعدة البيانات في كل طلب، وليس من الـ token.
  السحب يسري فورًا حتى لمن هو متصل الآن. الـ token يبقى لإثبات الهوية فقط.
- المنفّذ يقرر إن كان يحتاج ذاكرة مؤقتة قصيرة. إن فعل، يجب مسحها عند كل تغيير صلاحيات.

## الجزء 4: ما يراه المرشد من الطلاب

- **تعديل أثناء التنفيذ (2026-10-20):** بدل حقل جديد يُستعمل الحقل الموجود في الطالب
  `main_teacher` ("مرشد مسؤول"، معرّف المستخدم) لأنه بنفس المعنى. يظهر في نموذج الطالب كقائمة
  مستخدمين (بدون حساب النظام)، ويحدّده فقط من يملك `students.viewAll`.
- من يملك `students.view` بلا `viewAll` يرى الطالب إذا:
  - هو `main_teacher` للطالب، **أو**
  - الطالب في `list_students` لدرس فيه هو `teacher` أو `helper`.
- **قراري:** "الحوزة" اليوم = الدروس التي هو فيها معلم أو مساعد، بكل التواريخ. إن احتجتَ
  لاحقًا كيان "حوزة" منفصلًا (اسم، مرشدون، طلاب ثابتون)، هذا مشروع منفصل.
- الفحص في الخادم: قائمة الطلاب، طالب واحد، التعديل، الصورة، ورقة الحضور، وقائمة الطلاب في
  الدرس. طالب خارج النطاق = 404 (لا نكشف وجوده).
- قسم الرياضة: من يملك `sports` يرى كل ما في القسم. يُبنى مع القسم.

**الدروس مع النطاق (قراراتي):**
- المرشد يفتح أي درس كما اليوم، لكنه يرى فيه فقط الطلاب الذين في نطاقه، مع عدد "طلاب آخرون: N".
- **حفظ قائمة الطلاب لا يحذف المخفيين:** الخادم يدمج: يضيف ويحذف فقط طلابًا في نطاق المستخدم،
  والباقون في `list_students` يبقون كما هم. نفس الشيء في حفظ الحضور.
- **إضافة طالب ليس في النطاق:** نافذة اختيار الطلاب تعرض نطاقه، ومعها بحث برقم هوية كامل
  ومطابق. البحث يعيد الاسم فقط، وبعد الإضافة يدخل الطالب نطاقه لأنه صار في درسه.

## الجزء 5: شاشة الصلاحيات

### أين

صفحة المستخدم (`/users/:id`) تحصل على تبويب **"الصلاحيات"**. يظهر فقط لمن يملك
`permissions.manage` (والنظام). صفحة "حسابي" تُظهر للمستخدم صلاحياته **للقراءة فقط**
(قراري).

### الشكل

- أعلى التبويب: الدور الحالي، ومن غيّر الصلاحيات آخر مرة ومتى.
- قائمة الأقسام. كل قسم سطر بمفتاح تشغيل وسهم لفتح العمليات.
- مفتاح القسم بثلاث حالات: مفتوح كله، مفتوح جزئيًا، مغلق.
- بجانب كل عملية شارة المصدر: **من الدور** / **ممنوح** / **مسحوب**.
- عملية لا يستطيع المدير الحالي منحها: معطّلة مع تلميح "لا تملك هذه الصلاحية".
- زر **"إرجاع إلى صلاحيات الدور"**: يفرّغ الممنوح والمسحوب، بعد تأكيد.
- زر **"حفظ"**: يعرض ملخص التغييرات (ما أُضيف، ما سُحب) ويطلب تأكيدًا.
- الأقسام المحجوزة (الرياضة، المالية) لا تظهر قبل بنائها.
- الواجهة تخفي القوائم والأزرار حسب الصلاحيات الفعّالة، لكن الخادم يفحص كل شيء.

### الخادم

- `GET /api/user/me` يعيد `role` و`permissions` (القائمة الفعّالة).
- `GET /api/user/:tz/permissions`: الدور، الممنوح، المسحوب، الفعّال، ومن يستطيع
  المستخدم الحالي منحه. يحتاج `permissions.manage`.
- `PUT /api/user/:tz/permissions` بجسم `{ grants, revokes }`: يتحقق من كل قواعد مدير
  الصلاحيات، ويسجل في سجل التغييرات.
- `PUT /api/user/:tz/role`: يطبّق قواعد الترقية والتنزيل.
- حساب النظام كهدف: 404.

## الجزء 6: حساب النظام

- يُعرَّف بـ `SYSTEM_ADMIN_TZ` كما اليوم. إن لم يُضبط، لا أحد هو النظام.
- **مخفي:** يُستبعد من كل القوائم وردود الـ API: المستخدمون، اختيار المعلم والمساعد والمرشد
  المسؤول، مستلمو الإعلانات والبريد، العدّادات في لوحة التحكم. طلب `GET /api/user/:tz`
  له من غيره = 404.
- **الأفعال:** أي سجل (تقرير، إعلان، سجل تغييرات، `createdBy`) يكتبه يُخزَّن ويُعرض باسم
  **"النظام"**، وليس رقم هويته.
- **لا تتغير صلاحياته:** كل مسارات الصلاحيات والدور والحالة والحذف ترفضه كهدف.
- **تغيير كلمة المرور كل شهر:** حقل `passwordChangedAt`. إذا مرّ 30 يومًا، يعيد الدخول
  token محدودًا لا يسمح إلا بتغيير كلمة المرور، والواجهة تفتح شاشة التغيير إجباريًا.
- **لا يُحظر أبدًا:** عدّاد المحاولات الفاشلة يُحسب له، لكن لا حظر. **قراري:** كل 5 محاولات
  فاشلة متتالية يُرسَل بريد تنبيه لبريد النظام (لا إعلان في اللوحة، لأن الحساب مخفي).
- **البريد:** `SYSTEM_ADMIN_EMAIL` في ملف البيئة على الخادم (موجود اليوم في
  `ensureSystemAdmin.js` بقيمة افتراضية وهمية). صاحب المشروع أعطى عنوانًا حقيقيًا، يُضبط في
  البيئة **ولا يُكتب في الريبو** (الريبو عام). إن بقي فارغًا أو وهميًا، الخادم يكتب تحذيرًا عند
  التشغيل.
- **الاستعادة:**
  - عبر البريد: نفس `forgot-password` الموجود، إلى `SYSTEM_ADMIN_EMAIL`.
  - عبر مدير يملك `systemRecovery.reset`: الزر يعمل **فقط** إذا كان عدّاد المحاولات الفاشلة
    لحساب النظام 3 أو أكثر. الخادم يولّد كلمة مرور مؤقتة **ويرسلها لبريد النظام فقط**؛ المدير
    لا يراها أبدًا. فرض التغيير عند الدخول التالي. يُسجَّل في سجل التغييرات.
  - **طريق IT للحالات الحرجة:** سكريبت على الخادم (`server/scripts/`) يشغّله شخص IT له وصول
    للخادم: يرسل كلمة مرور مؤقتة لبريد النظام، أو يغيّر `SYSTEM_ADMIN_EMAIL` إن ضاع البريد.
    يُسجَّل في سجل التغييرات باسم "IT (خادم)".

## الجزء 7: حظر بعد محاولات فاشلة

- حقول جديدة في المستخدم: `failedLoginCount`, `lockedAt`.
- كل دخول بكلمة مرور خاطئة لحساب موجود: +1. دخول ناجح: يُصفَّر.
- عند الوصول إلى 5: `lockedAt = الآن`. من هنا كل محاولة دخول (حتى بكلمة صحيحة) ترجع
  `423` بـ `code: "ACCOUNT_LOCKED"` والرسالة:
  > تم حظر الحساب بسبب محاولات دخول فاشلة متكررة. يرجى التوجه إلى قسم تكنولوجيا المعلومات في الجمعية.
- `forgot-password` و`reset-password` لحساب محظور: نفس الرسالة، ولا يُرسل بريد.
- الحظر يُطبَّق على كل الحسابات **ما عدا النظام** (الجزء 6).
- **فك الحظر:** من يملك `users.unlock` (والنظام)، بزر في صفحة المستخدم. يصفّر العدّاد ويُسجَّل.
- حساب غير موجود: لا عدّاد، ونفس رسالة "رقم الهوية أو كلمة السر غير صحيحة".
- **خطر معروف (للعلم):** من يعرف رقم هوية أي موظف يستطيع حظره بخمس محاولات. حدّ المعدل
  الموجود يبطئ ذلك فقط. هذا ثمن قاعدة "لا فك ذاتي".

## الجزء 8: سجل التغييرات

- مجموعة جديدة `AuditLog`. كل سطر:
  `at`, `actor` (رقم الهوية أو `"system"`), `actorName`, `module`, `action`,
  `targetType`, `targetId`, `targetLabel`, `changes` (حقل: قبل/بعد), `ip`.
- **ما يُسجَّل:** إضافة/تعديل/حذف في الطلاب، المستخدمين، التقارير، الدروس، الحضور،
  الإعلانات، المركبات؛ في الملفات: رفع، حذف، تغيير اسم ملف أو مجلد، إنشاء مجلد، مشاركة
  وإلغاؤها؛ تغيير دور أو صلاحيات؛ حظر وفك حظر؛ استعادة النظام؛ ربط Google Drive.
- **لا يُسجَّل:** كلمات المرور، الـ hash، رموز OTP، الـ tokens (تُستبدل بـ `"***"`).
- **قراري:** السجل للإضافة فقط. لا مسار لحذفه أو تعديله، ولا حذف تلقائي في هذه المرحلة.
- **قراري:** سجل المركبات الحالي يبقى، والكتابة الجديدة تذهب للمكانين.
- **الشاشة:** صفحة `/audit` لمن يملك `audit.view`: جدول بتصفية حسب التاريخ، القسم، المنفّذ،
  ونوع العملية، وبحث باسم الهدف. صفحة كل مستخدم/طالب تعرض آخر تغييراته.

## الجزء 9: الانتقال يوم النشر

سكريبت ترحيل واحد (dry-run أولًا، ثم تنفيذ):

1. `role` = أعلى دور في `roles` (بعد توحيد كتابات `ادارة`/`إدارة`/`الادارة`/`الإدارة`).
   من عنده أكثر من دور: يُطبع في التقرير.
2. `vehiclePermissions` لغير المدير ← `permissionGrants` بمفاتيح `vehicles.*`.
3. لا شيء آخر يُمنح أو يُسحب: صلاحيات الأدوار = سلوك اليوم.
4. التقرير يذكر كل مستخدم وصلاحياته الفعّالة قبل وبعد. أي اختلاف غير الطلاب (الجزء 4) خطأ.

بعد الترحيل: `requireRole` وكل نسخ `isAdminUser` تُستبدل بـ `requirePermission(key)` و
`can(user, key)` من ملف واحد (`server/utils/permissions.js`).

## الترتيب المقترح

1. إصلاح المشاكل الأمنية + الحظر بعد 5 محاولات.
2. محرّك الصلاحيات + الترحيل + استبدال كل الفحوص (بلا تغيير سلوك).
3. سجل التغييرات.
4. شاشة الصلاحيات + تغيير الدور.
5. حساب النظام: الإخفاء، التغيير الشهري، الاستعادة.
6. نطاق الطلاب للمرشد.

كل خطوة تُراجَع وتُنشَر وحدها.
